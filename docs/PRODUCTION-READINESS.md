## Phase 0 — Blockers. Do not launch without these.

### 0.1 ✅ DONE — the database is now reproducible

**What the problem was.** The repo had 19 migration files; the live database had 27 applied. Ten migrations existed only on the server, one only in the repo, seven local files reused version numbers that already meant something else, and `0003_hero_slides.sql` declared three columns the live table didn't have. A fresh apply produced a database **missing six tables**. No staging environment, no recovery path, no local setup for a new developer.

**What was done.**
- `supabase/migrations/00000000000000_baseline.sql` — the complete schema, reconstructed from the live database: 20 tables, all RLS policies, functions, triggers, 3 storage buckets. Idempotent.
- `supabase/seed.sql` — all 109 content rows, generated by `scripts/dump-seed.mjs`, no personal data.
- `supabase/SETUP.md` — the 15-minute walkthrough for standing up a fresh project.
- `.env.example` — every variable documented.
- The 18 superseded files moved to `migrations/_archive/`, kept for their design rationale.

**Verified against a clean rebuild, not assumed.** `supabase db reset` on a local stack, then a column-level diff against production: **303 columns, identical, defaults included** (`md5 = 999d08aa304565e18d3000705d560701` both sides). RLS then tested behaviourally — anon reads published content, is blocked from drafts, writes and private tables; the profile trigger fires; a `content_editor` can write mosques but not news.

That testing caught a real bug: the first draft omitted the **table-level grants** to `anon`/`authenticated`, and since Postgres checks privileges before RLS, the rebuild failed with `permission denied for table news` with the policies never running. Supabase supplies those grants via its own default privileges, which is exactly why the original migrations never stated them — and why a rebuild anywhere else breaks. Section 10 of the baseline now does it explicitly.

**Remaining discipline:** every schema change from here is a file in `migrations/`, applied with `supabase db push`. Never the dashboard SQL editor alone — that is what caused the drift.

### 0.2 Re-upload the images when moving to a new project

**Correction to an earlier draft of this document:** the database is **not** empty. It holds 36 mosques, 10 `page_content` blobs, 10 team members, 7 news articles, 7 programs, 7 policies, 6 KPIs, 5 reports, 4 org levels and more — 109 rows, all captured in `seed.sql`. The earlier "0 rows" reading came from `list_tables`, which reports `reltuples` planner estimates that sit at 0 until autovacuum analyzes a table. Always use `count(*)`.

What *does* need doing when standing up a new project is **Storage**, which `seed.sql` cannot carry:

- Content rows reference image and PDF URLs on the **old** project's Storage host. Against a new project they 404.
- The `media` bucket is created empty by the baseline.

**Fix.** Either re-upload through the CMS (every image field has an upload button that rewrites the URL), or bulk-copy the bucket and rewrite the host with `update ... set image = replace(image, 'https://OLD-REF...', 'https://NEW-REF...')` per table. `SETUP.md` step 6 lists every column and jsonb blob holding a URL. Images referenced as site-relative paths (`/images/...`) come from `my-app/public/` and need nothing.

**Still worth doing regardless:** the section components fall back to hardcoded datasets in `lib/news.ts` etc. via `items={rows.length ? rows : undefined}`, so **an empty table and a failing query look identical**. Log loudly when a fallback is used, or a broken query will go unnoticed indefinitely.

**Effort:** 2–4 hours for the image migration. **Owner:** backend.

### 0.3 Notify someone when a form is submitted

Right now, a candidate submits a CV and a complainant submits a grievance with a promised tracking number, and **nothing happens**. No email, no SMS, no webhook. The only way anyone finds out is by opening `/admin/dashboard/applications` or `/complaints` and looking.

The complaints page tells the public it is a tracked channel. Not routing those to a human is an operational failure, and for a foundation handling grievances it is arguably a governance one.

**Fix.** Simplest path that fits the existing architecture — send from inside the two server actions (`app/(site)/careers/actions.ts`, `app/(site)/contact/actions.ts`) after the row is committed, via Resend or Amazon SES:

- To staff: "New complaint REQ-2026-000042 (شكوى) — <subject>", with a dashboard deep link. Never attach the file; link to the dashboard.
- To the submitter: acknowledgement carrying their `ticket_id` / `application_no`.

Send failures must not fail the submission — the row is already committed and the ticket number is already shown.

Alternative if you'd rather keep the app clean: a Supabase Database Webhook on `insert` for both tables → an Edge Function that sends the mail. More moving parts, but it also covers rows inserted out-of-band.

**Effort:** 1–2 days. **Owner:** backend.

### 0.4 Close the `contact_messages` spam hole

```sql
policy "contact insert public" ON public.contact_messages
  FOR INSERT WITH CHECK (true);
```

The anon key is shipped in every page. Anyone can `POST /rest/v1/contact_messages` in a loop and fill the table. There is no rate limit, no CAPTCHA, no honeypot. The two newer intake tables (`contact_requests`, `job_applications`) got this right — no anon policy, service-role-only writes — but the home-page contact form was never brought in line.

**Fix.**
```sql
drop policy "contact insert public" on public.contact_messages;
```
and change `components/home/contact-actions.ts` to use `createAdminClient()` instead of `supabaseAnon`, matching `submitContactRequest`. Add server-side validation (email shape, message length caps) while you're in there.

Then add abuse protection to **all three** public forms — see Phase 1.4.

**Effort:** 2–3 hours. **Owner:** backend.

## Phase 1 — Pre-launch. Complete before the domain goes live.

### 1.1 ✅ DONE — `/about/org-structure` now publishes CMS edits

`app/(site)/about/org-structure/page.tsx` read `getOrgLevels()` but omitted `export const dynamic = "force-dynamic"`, so Next prerendered it at build time and staff edits never appeared without a redeploy. Fixed.

Every other page was audited for the same omission using the build output's `○` (static) vs `ƒ` (dynamic) markers: this was the only one. The remaining static routes — `/about`, `/contact`, `/sitemap`, `/videos`, plus the `/about/leadership` and `/media-center` redirects — read no CMS data and are correctly static. `/about/org-structure` now builds as `ƒ`.

### 1.2 Validate `page_content` JSON — it silently destroys content today

`app/admin/dashboard/pages/actions.ts`:

```ts
try { content = JSON.parse(String(form.get("content") ?? "{}")); }
catch { content = {}; }          // ← writes an empty object over the live page copy
```

A malformed paste wipes a page's entire content, shows no error, and there is no undo and no version history. Recovery means a database restore.

**Fix:** on parse failure, `redirect(...?error=invalid-json)` and write nothing. Then add a `page_content_versions` table (or a `history jsonb[]` column) writing the previous value on every update, with a "restore" button. Given that these blobs hold the copy for nine public pages, this is cheap insurance.

### 1.3 Generate database types

Row types are hand-written in `lib/cms/fetchers.ts` and every field is read with `as string` / `as string[]`. **A column rename produces no type error** — it produces `undefined` on the live page.

```bash
supabase gen types typescript --project-id ibcnfufiyrnkfgxjkanr > lib/supabase/database.types.ts
```
Then type the clients (`createClient<Database>(...)`) and delete the casts. Add the generation to CI so drift is caught.

While you're there, delete `lib/cms/types.ts` — 155 lines of a superseded content model that nothing imports and that contradicts the live schema.

### 1.4 Rate limiting and bot protection on public forms

Three public write paths: contact message, complaint (with up to N file attachments), job application (with a CV upload). All unauthenticated, all unthrottled.

**Minimum:** Cloudflare Turnstile or hCaptcha on all three, verified server-side inside the action. Add a hidden honeypot field. Add per-IP throttling — Upstash Redis is the lowest-friction option that works on Vercel's edge, or use Vercel's own rate limiting.

Without this, the private buckets are a free file host and the inbox tables are a free spam target.

### 1.5 Fix the lint gate, then wire CI

`eslint.config.mjs` calls `globalIgnores([...])` with only `.next`, `out`, `build`, `next-env.d.ts`. That **replaces** the Next preset's defaults, so ESLint lints `public/` — including `public/pdf.worker.min.mjs` and `public/maplibre/mapbox-gl-rtl-text.js`. Those two vendored bundles produce essentially all 2680 warnings and 7 of the 12 errors.

```js
globalIgnores([".next/**", "out/**", "build/**", "public/**", "next-env.d.ts"]);
```

What remains is 5 real errors, all "Calling setState synchronously within an effect": `AlMajdouieLoader.tsx:32`, `ThemeProvider.tsx:28`, `expand-fade.tsx:25`, `use-mobile.ts:14`, `i18n/context.tsx:23`. All are the same hydration-safe mount-effect pattern; resolve with lazy `useState` initializers or `useSyncExternalStore`.

Then add a GitHub Action on every PR:
```
pnpm install --frozen-lockfile
pnpm lint          # must pass
npx tsc --noEmit   # must pass
pnpm build         # must pass
```

### 1.6 Error and loading boundaries

There is **no `error.tsx`, no `global-error.tsx`, and no `loading.tsx` anywhere in `app/`**. A thrown error in any server component shows the raw Next.js error page. `not-found.tsx` exists and is properly branded — the error equivalents are not.

Add:
- `app/(site)/error.tsx` — branded Arabic error page with a retry button
- `app/admin/dashboard/error.tsx` — admin-themed equivalent
- `app/global-error.tsx` — last-resort catch
- `app/(site)/loading.tsx` — skeleton, because every CMS page is `force-dynamic` and blocks on Supabase

### 1.7 Image weight — the LCP problem

`public/` is **66 MB across 396 files**, with twelve PNGs over 2 MB each (`focus-area/mehtag-2.png` at 2.6 MB, several mosque carousel images at 2.1 MB). `next/image` optimizes them on request, but the source files still bloat the deploy, and a cold-cache optimization of a 2.6 MB PNG is slow.

**Fix:** convert the photographic PNGs to WebP/AVIF at sane dimensions before they enter the repo. Target under 300 KB for full-bleed images. Expect a large LCP improvement on the homepage and focus-area pages.

`priority` is already used correctly on above-the-fold images (`HeroSlider`, `Header`, `NewsHero`, `LeadershipSpotlight`). The seven raw `<img>` tags are all admin thumbnails and YouTube posters — acceptable as-is.

### 1.8 Clear the Supabase advisors

**Security (15 warnings):**
```sql
-- 1. Pin search_path on the two ID generators
alter function public.next_contact_ticket_id()  set search_path = public;
alter function public.next_job_application_no() set search_path = public;

-- 2. Stop the RLS helpers being callable over /rest/v1/rpc/
revoke execute on function
  public.current_app_role(), public.is_super_admin(), public.is_content_staff(),
  public.is_news_staff(), public.is_staff(), public.handle_new_user()
from anon, authenticated;
```
3. Enable **leaked password protection** in Auth settings (one toggle, checks against HaveIBeenPwned).

**Performance (90 of 97 notices):** every content table has a `public read` SELECT policy *and* a `staff write` `FOR ALL` policy — and `FOR ALL` includes SELECT, so Postgres evaluates two permissive policies on every public read. Split each write policy into explicit `FOR INSERT` / `FOR UPDATE` / `FOR DELETE`. Also wrap `auth.uid()` as `(select auth.uid())` in the two `profiles` policies. Do this in one migration across all tables.

### 1.9 Storage hygiene

- Set a **file size limit and MIME allowlist on the `media` bucket** — it currently has neither. The 3 MB / 3000 px checks in `inline-upload.tsx` are client-side only and any signed-in staff member can bypass them via the API.
- **Orphaned objects are never deleted.** Deleting a news article leaves its image; replacing an image leaves the old one. `media` grows forever. Either add paired deletion in the content actions (as `complaints/actions.ts` and `applications/actions.ts` already do for the private buckets), or run a scheduled reconciliation job.

### 1.10 Domain, canonical URL, and env

- `.env` has `NEXT_PUBLIC_SITE_URL=https://www.almajdouie.org` (**with-www**), while `lib/site/config.ts` falls back to `https://almajdouie.org` (**no-www**). Pick one as canonical, 301 the other, and make sure the deployed env var matches — `metadataBase`, every canonical tag, the sitemap, `robots.txt`, and all JSON-LD `@id`s derive from it.
- That `.env` line also has a leading space after `=`. dotenv trims it, so it works, but tidy it.
- `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` is set but referenced nowhere in the code. Remove it.
- Set every variable in Vercel's project settings for **Production and Preview separately.** Confirm `SUPABASE_SERVICE_ROLE_KEY` is *not* marked as exposed to the browser.
- Rotate all keys once, at handover, since they have been in a local `.env` throughout development.

### 1.11 The `/videos` stub

`/videos` renders `PagePlaceholder` ("مكتبة الفيديو" — coming soon) but it **is listed in `app/sitemap.ts` and reachable from navigation.** Either build it (gallery data already supports `type = 'video'`) or remove it from the nav and the sitemap before crawlers index a placeholder.

### 1.12 Legal and PDPL

The site collects names, phone numbers, emails, CVs, and complaint attachments from Saudi residents. Under PDPL that needs:

- A **real privacy policy** — the page exists at `/privacy-policy` and renders from `page_content:privacy-policy`, which is **currently empty**. Legal must supply the text.
- A stated **retention period** for CVs and complaints, plus a mechanism to honor deletion requests. Deletion currently works (record + object together) but is manual and undocumented.
- The consent checkbox is already required and stored (`consent boolean`) on both forms — good — but it should reference the actual policy.
- Cookie/consent banner: currently none. The app sets only functional cookies (auth session, admin locale/theme) and `localStorage` for public locale/theme, so a banner may not be strictly required — get that confirmed rather than assumed.

## Phase 2 — Launch week

### 2.1 Backups, verified

Confirm the Supabase plan's backup frequency and retention, and enable **Point-in-Time Recovery**. Then actually perform a restore into a scratch project — an unverified backup is not a backup. With no soft deletes and no audit trail anywhere in this system, backups are the only recovery path for a mistaken delete.

### 2.2 Monitoring and alerting

There is **zero observability**: no error tracking, no analytics, no uptime check, no logging beyond Supabase's own.

- **Sentry** (or equivalent) for both server and client errors. Note that every fetcher in `lib/cms/fetchers.ts` swallows exceptions and returns `[]` — **add `captureException` inside those catch blocks**, or the outage that empties the homepage will be invisible.
- Uptime monitoring on `/` and `/admin`.
- Supabase alerts on database CPU, connection count, and storage growth.
- Analytics — Vercel Analytics or Plausible. Nothing is installed today, so there is no launch baseline to compare against.

### 2.3 Staging environment

One Supabase project, one environment, one set of keys. Content editors will be training on production.

Create a second Supabase project seeded from the Phase 0.1 baseline, point Vercel Preview deployments at it, and keep production credentials out of preview builds entirely.

Run against production immediately after the DNS cutover:

## Phase 3 — Post-launch hardening (first 90 days)

**Caching.** Every CMS page is `force-dynamic`, so **every page view is a live Supabase round-trip**. That is correct for a launch with unknown traffic, but it doesn't scale and it makes the site's uptime equal to Supabase's. Move to `revalidate` + tag-based invalidation: `unstable_cache` around the fetchers with a per-table tag, and `revalidateTag()` in the server actions. The `revalidatePath` calls already scattered through every `actions.ts` are the map of what invalidates what — that work is largely done.

**Tests.** There are none. Priority order:
1. RLS policy tests — for each role × table, assert allowed and denied. This is where a mistake is a security incident.
2. Server action tests for the two public intake actions, including the rollback path when the upload fails.
3. Playwright smoke test covering the checklist in §2.4.

**Audit trail.** Nothing records who changed what content or when. For a foundation publishing governance material, an `updated_by uuid references auth.users` column plus a content-change log is worth having before someone asks "who changed the board list?"

**Admin role gating in the UI.** `components/app-sidebar.tsx` only hides links. A `news_manager` who navigates to `/admin/dashboard/programs` sees the full editor and only discovers it's forbidden when the save silently fails. Add a role guard in each dashboard route's layout that redirects. Not a security hole — RLS holds — but a bad experience that will generate support tickets.

**Dark-mode icon inversion.** `globals.css` inverts icons by matching ~25 `src` substrings and specific `width` attributes. Any new icon in a new folder silently stays dark-on-dark, and renaming a folder breaks existing ones. Replace with an explicit `data-invert-on-dark` attribute on the images.

**Search.** `lib/cms/search.ts` runs seven parallel `ilike '%term%'` queries with no index support. Fine at current volume, linear-scan as content grows. Move to Postgres full-text search (`tsvector` + GIN, with an Arabic configuration) when the catalogue gets large.

**Code cleanup.** Four `.js` components in `components/focus-area/detail/`; four orphaned `.module.css` files in `components/focus-area/economic/` with no component; `str`/`lines`/`csv` parsers duplicated across ~15 `actions.ts` files; `middleware.ts` deprecated in Next 16 in favor of `proxy.ts`.

**English SEO.** The English toggle is client-side only — there are no `/en` routes, no `hreflang`, and all metadata is Arabic. Crawlers never see the English content. If English discoverability matters to the foundation, that is a real i18n routing project, not a tweak. Scope it deliberately.
